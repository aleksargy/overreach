# Overreach

A personal PWA that replaces Garmin Connect and Hevy for one person (Alex). It pulls runs, football, rides, swims and watch health data from the Garmin Personal API, and has its own strength logger. It's deployed to Netlify and added to an iPhone home screen. The name is a placeholder (see Renaming).

Look and feel is the top priority, and the look is the app's own: read the design rules before changing any screen. Running, football and lifting are what Alex trains, so each has a tab; rides and swims are synced and shown but get no new work for now.

`README.md` is the guide for people: setup, secrets, deploying, keeping it running. `docs/` has the decisions and why (`decisions.md`), the Garmin API notes (`garmin-api.md`), and what's next, what's unchecked and the ideas on the shelf (`roadmap.md`).

## Working here

- Show it early: a screenshot or a preview before the polish, and let Alex react. Look and feel decides.
- Little, and well worked: a screen shows a few things Alex can read at a glance, each done properly. No walls of text, no "how it's worked out", nothing he has to decode. When in doubt, leave it out. Running, football and lifting each have a tab, Today and Body stay a short dashboard, and rides and swims are shown but not extended.
- Say something only when it's news: insights come from `standout` (how rare a reading is in Alex's own history), not from thresholds or stock sentences. A screen picks out one reading at most, and on an ordinary day it picks out nothing.
- The analysis is personal: measure against Alex's own baseline, not population norms, and say plainly when the data can't support a claim.
- Few Garmin calls: new fetches go inside the sync step, never a new poll.
- Every change goes through a branch and a pull request; `check` has to pass, and main can't be pushed to directly. Commits are authored as aleksargy, with no AI co-author or session trailers (`.claude/settings.json` turns them off).
- Secrets never go in the repo, the chat or the browser bundle (see Secrets).

## Commands

```sh
npm install          # Node 22 (.nvmrc)
npm run dev          # app on :5173, sample data until the first sync; /api is proxied to :8788
npm run dev:api      # the real functions + a fake Garmin with a year of history on :8788, passphrase "dev"
npm run dev:real     # the same against your real Garmin account: key from .env.local through varlock, 90 days back
npm test             # sync engine against the fake Garmin, the functions against a local Blobs server, the pure logic
npm run typecheck
npm run format       # Prettier (pinned): no semicolons, single quotes, width 180; CI runs format:check
npm run check:env    # varlock audit: every env var the code reads is declared in .env.schema
npm run build        # tsc + vite build into dist/
npm run build:preview  # one self-contained HTML file: dist-preview/preview.html
npm run screens      # every screen at 390 × 844, sample and live, into screens/; --race switches the race card on, --bar keeps the tab bar in, --webkit uses Safari's engine
npm run icons        # re-render the icon PNGs (Playwright)
```

To see live mode locally, run `npm run dev:api` and `npm run dev` together, open Settings, type `dev` as the passphrase and tap Sync now. The fake's Blobs live in `.netlify/dev-blobs`; delete that folder to start over. `npm run dev:real` keeps its store in `.netlify/real-blobs`, so real and fake data never mix, and it stays on this Mac. Both listen on 127.0.0.1 only.

The preview build uses a memory router. A bare hash picks the first screen: `#run`, `#football`, `#body`, `#feed`, `#lift`, `#prefs`.

## Layout

- `src/screens/` one folder per area: today (plus the + log sheet), run (plus the race report and ghosts), football (log sheet with the points editor, rating reveal, match report, player card), lift (the tab, a workout and its editor, the logger overlay, a lift's page, sessions), body, feed ("All activity", opened from Today, plus activity detail) and settings.
- `src/components/` shared UI (`ui/`, with the ring and cross beside a match's points in `ui/Mark.tsx`), charts (`charts/`), icons (`icons/`, the tab bar's are drawn in `tabs.tsx`), the tab bar, the activity row.
- `src/data/` the store, the derived world, the API client, the backup of what you type, types, exercises, and generated sample data (`sample/`).
- `src/lib/` pure logic with no React: the running model and best times (`running.ts`), races and race reports (`race.ts`), ghosts (`ghost.ts`), what's worth saying (`standout.ts`, fed by `series.ts`), football rating and analysis, training load, lifting targets, bests and progress (`lift.ts`), schedule guessing, backup merging, formatting.
- `netlify/functions/` `status`, `sync` (POST), `data`, `stream`, `user` (the copy of what you type), and `scheduled-sync` (once a day, 05:00 UTC).
- `netlify/lib/` the Garmin client, the sync engine, Garmin-to-app mapping, FIT decoding, run weather from Open-Meteo, the Blobs wrapper, request helpers.
- `tests/` the fake Garmin (realistic shapes, range limits, FIT files, slow answers, plus a fake Open-Meteo) and the tests.
- `scripts/` the local API, screenshots, icon rendering, the preview inliner.
- `.github/` `ci.yml` (checks and a preview for every pull request), `deploy.yml` (main to Netlify), Dependabot, the pull request template.
- `.claude/` Claude Code's project settings (permissions, a Prettier hook, attribution off) and skills: `check-screens`, `garmin-shapes`.
- `docs/` decisions, Garmin API notes, roadmap, and the Floodlight design with its mockups (`design/`).

## How data flows

- **Store** (`src/data/store.ts`, zustand) holds what the person types: matches, workouts, routines, custom exercises, weigh-ins, profile and sync settings. It's saved to IndexedDB under `overreach:user:v1`; the Garmin cache is saved separately under `overreach:garmin:v1`. Nothing is written until IndexedDB has answered at start-up, so a slow start can't save defaults over real data. Saves happen straight away, except while typing into a live workout (300 ms pause), and any pending save is flushed when the app is hidden.
- **Backup.** What you type is also copied to the server: `src/data/backup.ts` sends it to `/api/user` (Blobs key `user`) a few seconds after each change once the phone has synced, and again on open if a copy didn't make it. The first sync on a phone with none of your data (a new phone, a reset, a removed home-screen app) brings it back. Lists merge by id with the phone's version winning, a match deleted on the phone stays deleted, and the server never swaps a full copy for an empty one. A workout of your own counts as data, like a match does. Settings also exports a file and restores from one (`src/lib/backup.ts`).
- **World** (`src/data/world.ts`, `useWorld()`) derives everything the screens show: Garmin activities (or sample data before the first sync) merged with logged workouts and matches, plus load, the weekly schedule and unrated games. Screens read the world and write through store actions.
- **Load** is Garmin's training load where the watch worked one out, and TRIMP from time in zones where it didn't. Zones are your Garmin zones once synced, 50–90% of max HR before. Max and resting HR come from the watch too: Garmin's zone settings on every sync, or else what it measured (`heartRatesFrom`: resting is the middle of the last 28 mornings, max the second highest of the year's three highest readings). Settings has only your name for you, nothing to set by hand.
- **What's worth saying** (`src/lib/standout.ts`). A reading is news when it's the highest or lowest Alex has had in a long while, judged only against his own readings: the lowest HRV in three weeks, the longest run in two months, the heaviest squat yet. `standout` goes through series built in `series.ts` (mornings, runs, lifts, games, weigh-ins), takes the latest reading of each, counts the earlier ones it beats and says the rarest in those terms. A morning's reading has to be the most extreme in three weeks; a run has to beat the ten before it, a game the eight before it, a lift its last three sessions; and "yet" is only said once there's a fair run of history. There are no thresholds per metric and no stock sentences, so most days most things say nothing. Each tab shows its own for a day or two after it happens, as the reading on a tile with one sage line under it (`StandoutLine`). Today takes the rarest of them only if it's twice as rare as its tab asks for and still fresh (`headline`), and shows it in the tile beside the next game, where your weight sits on an ordinary day: replayed over two months of Alex's data that was about two mornings a week, with nothing the rest.
- **Run tab** is kept small: this week's distance against the usual week, over twelve weeks of bars; Fitness, one number (the pace held at an easy heart rate, from the running model's engine) and which way it's going; Bests, the fastest 1 km, 5 km, 10 km, half and marathon of the last year (`bestsOf`; a race counts at its finish time, since a watch measures a course long); races, and recent runs. Endurance, critical speed with race predictions, what hills and heat cost, and the easy and hard split were taken out on 10 Nov 2026: Alex couldn't read them. Don't add an insight back without him asking.
- **Race report.** A race is a run marked as a race on the watch, or the one on the day of the race set in Settings. The report scales the watch's distance to the race distance (watches measure courses long) and takes the finish from the watch: splits every 1 or 5 km, the gap to goal pace (or to an even pace) along the way, the halves, where heart rate drifted and where the pace fell away, the best before at that distance. The Run tab lists races from the last year, and for a month after race day the race card shows the result.
- **Ghosts.** A run's ghosts are your earlier runs that share a stretch of it the same way round, raced over that stretch. Each run summary keeps an outline (a point every 100 m, `ROUTE_STEP`), and `sharedStretch` walks your outline point by point for the longest stretch the other run also ran: each point within 40 m of its route and reached at about your rate, a miss of up to two points bridged, and no detour (neither run gets more than 150 m ahead of the other at the same place, beyond a steady drift from a watch measuring long). A stretch counts from 3 km, and on longer runs from 30% of the run, never more than 5 km (`stretchNeeded`). `coursesOf` groups the ghosts that share about the same stretch and races them over the part they all ran: up to three stretches a run, longest first, eight ghosts each, and a shorter one only when it brings in more ghosts. The race is on moving time, so waiting for GPS or at a crossing doesn't count. The card on a run only shows when it has ghosts, and the screen loads only their streams: pills pick the stretch, and it plays them back together with the order on the road, the gap to each at the same places, and heart rate against your best there. Run streams from the last year are stored in Blobs during sync, so loading ghosts costs no Garmin calls; older runs have no outline and aren't ghosts.
- **Race** (`src/lib/race.ts`) is off unless "Training for a race" is on in Settings. Then the Run tab opens with a countdown and the goal pace, and for a month after race day with the result, circled if it beat the goal, and the way into the race report.
- **Rating prompts** only cover games from the last 14 days that you haven't rated or skipped (`gamesToRate`); a swipe left skips one, and skips are backed up with the rest of what you type.
- **Sample mode** shows generated data with a "Sample data" badge until the first successful sync. After that the app is in live mode.
- **Streams** (HR, speed, GPS, laps) load per activity from `/api/stream?id=g-…`. The server decodes the FIT file once and caches it in Blobs.
- **Run summaries.** During sync the server reads each run's FIT file (runs from the last year, `RUN_DAYS`) and stores a small `run` summary on the activity: speed, heart rate and grade minute by minute, best efforts from 1 to 60 minutes, the fastest time over 1 km, 5 km, 10 km, a half and a marathon (`bestD`, by the clock, so a stop counts), the start rounded to 0.1° (about 10 km), the route's outline for ghosts, and the temperature and dew point. So the Run tab never needs a stream download.
- **Running model** (`src/lib/running.ts`, `useRunModel()`) is fitted in the browser from those summaries. A within-run regression of heart rate on speed, climb, descent and minutes gives shared slopes; backfitting then splits each run's residual into fitness (a 12-day kernel), heat (bpm per °C above 12) and the football hangover (runs within 36 hours of a game), so a hot day or tired legs don't read as lost fitness. What the screens use is the aerobic engine and its trend: pace at a fixed heart rate (68% of reserve), flat, cool and fresh. The heat, hill and football costs worked out along the way aren't shown. The sample data has these effects built in, and `tests/running.test.ts` checks the model finds them.
- **Lifting** (`src/lib/lift.ts`). Workouts (`Routine`) are lists Alex makes himself: exercises in the order he does them, with a number of sets each. The list starts empty, and the first thing the Lift tab asks for is a workout of your own; there are no starter workouts and no import from another app (Alex chose to start fresh). After that the tab opens on the next one up, the one that's waited longest (`nextRoutine`), with what to lift on every exercise and Start workout. The plan is double progression (`targetFor`): each exercise has a rep range; the top of the range on every set earns more weight (the exercise's `increment`), starting again from the bottom of the range; short of that the weight stays and the target is one more rep than the weakest set; under the range twice running at the same weight takes a tenth off. Bodyweight work adds a rep and holds add 5 s. There's no RPE in it: a set is a weight, reps and a tick.
- **Logging a workout** happens in a full-screen overlay that minimises to a bar above the tabs. Each set shows last time's numbers and is prefilled with the target, so a tick logs it; a weight you type carries down the sets after it; a rest timer starts on each tick. Finishing asks how it felt in four words, stored on the 1–10 scale training load is worked out from (`srpeLoad`). The session's page circles what was a new best (`recordsIn`: the heaviest yet, or the most reps at that weight or heavier). Each lift's page has next time's target, the rule in one line, and the heaviest set of each session over time; Progress on the Lift tab is the lifts done most in the last eight weeks (`progressOf`).
- **Football.** Match ratings and the player card are computed in `src/lib/football.ts` from what's logged (score, goals, assists, how it felt, what went well and badly) plus the watch's physical numbers when the game was recorded.
- **Points.** What went well and badly is written in your own words, two columns in the log sheet. The only suggestions are points written before in your own words: nothing ready-made (the old fixed moments aren't offered, and the boxes have no example text). Each point counts ±0.15 on the rating, a big one ±0.3, and together they move it 0.6 at most (`POINT`, `BIG_POINT`, `POINTS_CAP`); the breakdown lists each one, then the cap. A big point is quoted in the match report's rating lines. Points that come up in more than one of the last ten games show under form. Games rated before this had `moments`: `withPoints` reads them as points, on load and in any copy merged back in.
- **Head to head.** Your record against each opponent you've met twice or more, in the format you're looking at, across seasons, with the bogey team and the favourite fixture. A name matches however it was typed. The match report says which meeting it was.
- **Season heatmap.** During sync each game keeps a `trace`: a point every 15 s of play, in metres from where it was played. `seasonPitch` frames each ground from every game on it, so a winger stays out wide, then turns every half to face the same way: halves are matched to each other (the toss picks the ends and they change at half time), and the side of halfway you stood on at kick-off, the second half's most of all, says which end was yours. When that vote is close the screen says it may be back to front and drops the arrow.
- **Formats.** Alex usually plays 11-a-side and sometimes 7s, and the two aren't compared like for like. The rating's baseline, the thrashing margin (`BIG_MARGIN`) and the match report's medians only use games of the same format, and the Football tab splits season, form, records and matches by format (the switch shows once more than one format has been played). The player card covers every format but judges each game against its own first (`PAR` for goals and assists, `ENGINE_RANGE` for metres per minute and sprints), so only top speed and the rating are shared as they are. An unrated watch game takes its format from `formatOf`: its rated match, else what's usually played at that time of the week (`usualFormatAt`: same weekday, within two hours), else the format you've played most (`usualOf`). The log sheet starts with that format and the team and position last used in it (in a format you haven't logged yet, the team you last played for and the position you've played most); the opponent starts blank. There are no football settings, and the player card is drawn for the position you've played most that season.

## Server (Netlify)

- Environment variables: `GARMIN_PERSONAL_API_KEY` (from connect.garmin.com/app/settings/personalApiToken) and `OVERREACH_PASSPHRASE` (any phrase; the same one is typed into Settings). `OVERREACH_HISTORY_DAYS` shortens the history walk for local runs. All of them are listed in `.env.schema`. The Garmin key must never reach browser code.
- Every endpoint checks the `x-overreach-key` header against the passphrase.
- Data lives in the Blobs store `overreach` (strong consistency). Keys: `state`, `activities`, `dailies`, `body`, `user`, `stream/<id>`, `shapes`, `token`, `lock`.
- Opening the app is the main trigger: it runs a step without forcing, and the server only calls Garmin if its last recent pass was more than 10 minutes ago, however often the app opens. The app downloads `/api/data` only when the server's `dataAt` has moved. Sync now in Settings forces a fresh pass. A job at 05:00 UTC is the safety net (Alex asked for few calls, to stay clear of rate limits and junk requests).
- Sync runs in steps that fit Netlify's limits: from the app, 20 s of work per call with every Garmin request stopped by 24 s (Netlify's docs give synchronous functions 30 s in one place and 60 s in another); for the morning job, 18 s and 22 s (scheduled functions get 30 s); at most 30 Garmin calls per step. A FIT download the deadline cuts off stays first in line for the next step. A lock in Blobs stops the job and the app from overlapping. Each step does, in order: the recent pass (health data since the last pass, at least two weeks; if that's over 180 days the health history is walked again), run and football FIT files still to read, summaries made before they last gained something (`FOOTBALL_SUMMARY`, `RUN_SUMMARY`), brought up to date from the streams stored in Blobs, eight at a time and with no Garmin call (sync isn't done until they all are); the detail of runs and games from the last 30 days (the RPE and feel you enter on the watch; one call each, read once), weather for new runs, the activity backfill (two years), the health backfill (180-day chunks; sleep only for 120 days).
- Garmin limits per call: activities 50 per page, daily summaries and HRV 180 days, sleep 28 days, weight 365 days. Over-long ranges come back as empty 400s or 500s.
- A 429 pauses the sync and keeps what was fetched. A 401 re-exchanges the token once. An endpoint that keeps failing is named in `warnings` and skipped.
- Weather comes from Open-Meteo (free, no key): the archive API, or the forecast API for runs in the last six days. Only the rounded location and a date range go out, one request per place. A failure waits 30 minutes and never holds up the sync.
- `/api/status?shapes` returns the field types Garmin actually sent, without any values. Use it to fix `netlify/lib/mapping.ts` against real data (the `garmin-shapes` skill); the readers there are deliberately tolerant.
- The Personal API is pull-only (no webhooks, no pushing workouts), and keys expire after 30 days to a year and must be renewed by hand.

## Secrets

- `.env.schema` lists every variable and which are sensitive; varlock checks it, and `npm run check:env` fails if the code reads one that isn't listed. Values never go in git or the chat.
- The deployed site gets its values from Netlify's environment variables, set for the Production context only, so a preview never has them. Previews also deploy without functions.
- On this Mac, `.env.local` (gitignored) holds `varlock("local:…")` refs that only this Mac can decrypt. `npm run dev:real` runs through `varlock run`, which redacts sensitive values from piped output.
- The deploy workflow uses a `NETLIFY_AUTH_TOKEN` secret and a `NETLIFY_SITE_ID` variable in GitHub.
- Never give a secret a `VITE_` prefix: Vite puts those in the browser bundle.
- Don't read `.env.local` or `.netlify/real-blobs`, and don't run `varlock reveal` or `varlock printenv`; `.claude/settings.json` denies them. To call the deployed API, let varlock pass the passphrase (see the `garmin-shapes` skill).

## Design rules

The look is Floodlight, which Alex picked on 13 Nov 2026 to replace the board (slate and chalk). `docs/design/floodlight.md` has the full rules and the tokens, with a mockup of each main screen in `docs/design/floodlight/` (a PNG, and the HTML with the exact values). Graphite and big rounded tiles: each tab has one hero tile tinted in its own muted colour, and everything else sits on plain graphite tiles. Colour is soft, never neon, and nothing glows or blurs. It still isn't the stock dark dashboard: no frosted glass, no glows or blurred blobs, no Geist or Inter.

- **Graphite and muted colour.** Dark only. The page is `ink-0`, tiles and sheets `ink-1`, the tab bar, chips, icon buttons and hairlines inside a tile `ink-2`, pressed `ink-3`; text is `fg`, fading through `fg-2` to `fg-4`. Each tab has a set: the colour itself (lines, bars, dots), a tint for its hero tile, a label colour and a headline colour for text on the tint (`football` sage, `run` dusty blue, `body` mauve, `strength` lilac, and `gold` for the match rating and the card), used as `bg-run-tint`, `text-run-label`, `text-run-head`; reading text on a tint is its headline colour at 80%. Sage also marks anything new: a best, the one thing worth a look. `good` and `bad` say better or worse, z1 to z5 are heart-rate zones (the ochre z4 only in zone charts: Alex doesn't like orange, so ratings in the 5s are red), and `warn` is only the Sample data pill. Colours are RGB variables in `src/styles/index.css`, used through Tailwind; never a hex colour in a component (the card's metals and the pitch are variables too).
- **Type.** Bricolage Grotesque (`.display`, `.num`, `.num-hero`, `.t-page`) for anything big: titles, hero numbers and words, numbers on tiles, the card. It's the full Fontsource build with optical sizes, which is what the mockups were drawn with (the width-only one sets about 5% wider). Manrope for everything else: labels (`.label`, 12.5 px), reading, buttons, pills. Sentence case; the only capitals are the card's stat names and position.
- **Tiles.** `.tile` is `ink-1` with 22 px corners and 16 px padding, no border and no shadow; `.hero` is a tab's tinted one, 26 px corners and 18 px padding (`hero bg-run-tint`). Tiles sit 10 px apart. A section is a tile with a small label at its top (`Section`; `bare` for a row of tiles of its own). Lists are rows inside one tile, split by hairlines (`.list`). A tile inside a tile, or in a sheet, steps up a shade.
- **Pills.** Anything you press or pick is a pill: `.btn-primary` (a 50 px `fg` pill), `.btn-ghost` (`ink-2`), `.chip` (36 px), `.round` (a 40 px circle, `.round-on` for the solid +), and `Segmented`, a pill track with the picked option a solid pill that slides across. A status is `.pill`, on its colour at about an eighth (`pill [--p:var(--good)]`). On a hero tile a button takes the tint's headline colour (Lift's Start workout). Done is a filled circle in the sport's colour, and `Mark` is the ring or cross beside what went well or badly.
- **Floating, not docked.** The tab bar is a pill floating 26 px above the bottom: idle tabs are round icons, the current one a solid pill with its name that slides between them. The rest timer and a minimised workout are `ink-2` tiles floating above it. A pushed screen keeps round Back and action buttons at the top, with its title in a pill once it scrolls. Sheets are `ink-1` with 26 px top corners and a handle; behind them the page dims, and nothing is blurred.
- **Charts.** Lines 2.5 px with round ends in the tab's colour, the latest reading a `fg` dot (a ring when it's the one worth a look), raw readings faint dots, bars as capsules faint in their colour with the one that matters solid, progress as an 8 px track. No grids and no axes; a label only where it's needed. The heatmap is a dark pitch with soft blobs from sage to gold.
- **Words.** No generated copy anywhere: no back-page headlines, standfirsts, "you did this" summaries or quips (Alex: "i dont want any cringe one liners or fake summaries"). Screens show numbers, labels and Alex's own words (his points and notes). The one sentence the app makes up is a `standout`, a plain statement of a rare reading. No explanations of method, no captions that restate a chart, and empty things are hidden rather than shown as dashes or zeros.
- **The player card** is a black shield edged in its tier's metal (`.metal-gold`, `.metal-silver`, `.metal-bronze`; 85+ is gold too): the overall and position top left, "In form" when form is 85 or more, the six stats under the name.
- Phone first (390 px wide), 16 px gutters that respect safe areas, content starting 58 px down. Tabs: Today, Run, Football, Lift, Body, each with its own drawn icon. Input happens in sheets (the + on Today opens the log sheet) or, for a workout, in the full-screen logger; reports are full screens.
- Motion comes from `motion/react` springs; hero numbers can count up (`Ticker`). `MotionConfig reducedMotion="user"` is respected.
- After a UI change, look at it at 390 × 844 in both sample and live mode: `npm run screens` (the `check-screens` skill), and compare a drawn screen with its mockup. `--webkit` renders in Safari's engine, which is what the home-screen app runs on.

## Gotchas

- Tailwind opacity modifiers on the theme colours must come from Tailwind's scale (`/5`, `/10` up to `/95`) or be arbitrary (`/[0.05]`). Something like `bg-fg/97` silently produces no CSS.
- The sample data in `src/data/sample/` is deterministic (seeded from dates and ids) and has the running effects built in that `tests/running.test.ts` checks, so run `npm test` after changing it. It plays 11s on Sunday mornings and 7s every other Tuesday evening; that schedule is made up, not Alex's. The sample runner has one route for each distance they run from home and a parkrun course, so ghosts and races show, and long runs go round the 8 km loop before a loop of their own, so a shared stretch shows too; the sample player is a right-sided midfielder on the same ground each week, and the ends change at half time. The sample lifter has four workouts (`SAMPLE_ROUTINES`) and works through them by double progression, so targets, bests and progress show; they appear on sample data only.
- A number that ticks over (a clock, a rest timer) gets `tabular-nums`, or it jitters as its digits change width: Bricolage Grotesque has tabular figures. Manrope has none, so ticking numbers go in the display face.
- Tailwind only makes the classes it finds written out in full in the source. A class put together from parts (`grid-cols-[${…}]`) silently does nothing; spell each one out.
- Serve `dist-preview/preview.html` as `text/html; charset=utf-8`, or curly quotes and middle dots turn into mojibake.
- Saved shapes are versioned (`UserData.version`, `SyncState.v`, the `:v1` storage keys, the backup's `v`, and each run and game summary's `v`: bump `RUN_SUMMARY` or `FOOTBALL_SUMMARY` when a summary gains something, and sync brings the older ones up to date from the stored streams; run summaries are on 3, which added best times). `UserData.version` 2 is matches with points instead of moments (`withPoints`, run by `hydrate` and on every copy merged in); 3 is workouts starting empty: every phone used to begin with the four sample workouts, and `withoutStarters` leaves behind the ones never changed or used, on load and in any copy merged in. When a saved shape changes, bump its version and migrate on load (`hydrate`, `loadAll`), because real data already lives on the phone and in Blobs.
- When a fix to `netlify/lib/mapping.ts` means stored data was read wrong, bump `HEALTH_MAPPING` (days) or `ACTIVITY_MAPPING` (activities) in `sync.ts`: the next steps read that history again (about ten calls for days, a page per 50 activities, no FIT files).

## Renaming

Change `APP_NAME` in `src/config.ts`, the `<title>` in `index.html`, and `name`/`short_name` in `public/manifest.webmanifest`. Run `npm run icons` if the mark changes. The service worker's cache is named after each build, so installed copies pick up the new name and icons on the next deploy. The Blobs store name and the storage keys say "overreach"; leave them unless you also migrate the data.

## Deploying

GitHub Actions deploys; Netlify doesn't build from git. `ci.yml` checks every pull request and puts up a preview of it (sample data, no functions). `deploy.yml` checks main again and deploys it to production, except for changes that only touch docs or Claude's settings, because each production deploy costs 15 of the free plan's 300 monthly credits.
